### 1. Запуск всех тестов проекта (ЛР1 + ЛР2):
```powershell
python -m unittest discover -v
```
> Автоматически находит и запускает **45 тестов** (22 теста для ЛР1 и 23 теста для модуля доставки).

> Все 22 теста проходят успешно (`OK`, 100%).

## 🎯 Методология тест-дизайна (вопросы преподавателя)

Преподаватель обязательно спросит: *«По какому принципу вы придумывали тестовые случаи?»*

1. **Классы эквивалентности (Equivalence Partitioning):**
   * **Вес посылки:**
     * Класс 1 (до 5 кг): базовый тариф без надбавки (коэф. 1.0). Тест: `2.0` кг.
     * Класс 2 (от 5 до 20 кг): надбавка 20% (коэф. 1.2). Тест: `10.0` кг.
     * Класс 3 (от 20 до 50 кг): надбавка 50% (коэф. 1.5). Тест: `25.0` кг.
     * Недопустимые классы: отрицательный вес (`-5.0`), меньше минимума (`0.05`), выше максимума (`50.1`).
   * **Тип отправления:**
     * Валидные классы: «обычный» (+0 руб.), «хрупкий» (+300 руб.), «опасный» (+1000 руб.).
     * Невалидный класс: неизвестный тип («документы» $\rightarrow$ возврат ошибки).
   * **Тип доставки:**
     * Обычная (`is_express=False`) vs Экспресс (`is_express=True`).

2. **Граничные значения (Boundary Value Analysis):**
   * Тестируются границы допустимых диапазонов и точки переключения тарифов:
     * Минимальный вес: `0.1` кг (валидная граница), `0.05` кг (нарушение границы снизу).
     * Максимальный вес: `50.0` кг (валидная граница), `50.1` кг (нарушение границы сверху).
     * Точки перехода тарифов: `5.0` кг (порог без наценки), `20.0` кг (порог коэффициента 1.5).
     * Дистанция: `1` км (мин. граница), `0` км (нарушение), `5000` км (макс. граница), `5001` км (нарушение).

## 💬 Частые вопросы преподавателя к защите ЛР2

**В: Почему упавшие тесты считаются успехом лабораторной работы, а не вашей ошибкой?**  
*О: По условиям задания ЛР2 нам предоставлен сторонний код с преднамеренно заложенными дефектами. Задача тестировщика — не «подогнать» тесты под кривой код, а написать тесты по спецификации предметной области. Падение тестов объективно локализует несоответствия кода бизнес-требованиям, что зафиксировано в пунктах Б и В отчета.*

**В: Почему экспресс-доставка за 0 дней считается дефектом?**  
*О: При целочисленном делении `1 // 2` получается 0 дней. В результате дата доставки совпадает с датой отправки (`2026-09-03`). В междугородней логистике (авто/ж/д/авиа) доставка не может происходить мгновенно в 0 секунд — минимальный технологический срок должен составлять не менее 1 дня.*

**В: Как вы рассчитывали ожидаемую дату доставки?**  
*О: От фиксированной даты отправки `2026-09-03` прибавляется количество дней по формуле: `days_needed = max(1, distance // 500)`. Например, для дистанции 1500 км: `1500 // 500 = 3` дня. `2026-09-03 + 3 дня = 2026-09-06`.*

**В: Чем отличается assertEqual от assertGreater?**  
*О: `assertEqual(a, b)` проверяет строгое равенство значений `a == b`. `assertGreater(a, b)` проверяет отношение `a > b` — это было использовано в тесте `test_express_delivery_cost_surcharge`, чтобы доказать, что экспресс-доставка должна быть строго дороже стандартной.*

**В: Как гарантируется независимость тестов?**  
*О: Каждый тест оформлен отдельным методом с префиксом `test_`, не использует глобальных изменяемых переменных и не зависит от порядка запуска других тестовых методов.*

**В: Назовите 4 принципа ООП и какой из них применяется в этой лабораторной?**  
*О: Четыре принципа: инкапсуляция, наследование, полиморфизм и абстракция. В ЛР2 ключевым является **наследование**: тестовые классы наследуются от базового класса `unittest.TestCase` (`class TestDeliveryService(unittest.TestCase)`), получая от него ассерты и раннер. Также работает **полиморфизм**: тестовый раннер взаимодействует со всеми наборами тестов единообразно через базовый интерфейс `TestCase`.*

**В: Какие assert-методы есть в unittest и какие использованы в нашем проекте?**  
*О: В наших 45 тестах задействовано 7 видов проверок (всего 90 вызовов):*
* `assertEqual` (48 раз) — строгое равенство значений (стоимость, даты доставки, пустое сообщение об ошибке);
* `assertIn` (17 раз) — вхождение подстроки (проверка текста ошибок валидации, наличие записей в логах);
* `assertFalse` (14 раз) — негативные тесты (неуспешная валидация невалидных данных);
* `assertTrue` (6 раз) — позитивные тесты (успех валидации, существование файла логов);
* `assertNotIn` (3 раза) — безопасность (проверка, что открытый пароль не утек в лог или маску);
* `assertGreater` (1 раз) — проверка `cost_exp > cost_std` (наценка за экспресс);
* `assertNotEqual` (1 раз) — неравенство хеш-масок разных паролей.  
*(Другие методы в unittest: `assertIs`, `assertIsNone`, `assertRaises`, `assertAlmostEqual`).*

**В: Каким образом unittest понимает, что перед ним тесты и их нужно выполнить?**  
*О: По принципу «соглашение важнее конфигурации» (Convention over Configuration) через интроспекцию:*
1. *По файлам:* ищет модули по шаблону `test*.py` (`test_delivery.py`, `test_my_project.py`);
2. *По классам:* находит только классы-наследники `unittest.TestCase` (`issubclass`);
3. *По методам:* запускает только методы с префиксом `test_` (`dir(cls)`). Вспомогательные методы без префикса `test_` игнорируются.

**В: В чем смысл конструкции `if __name__ == "__main__": unittest.main()` и почему именно `__main__`?**  
*О: Служебная переменная `__name__` хранит контекст выполнения. Если файл запущен напрямую как точка входа (`python tests/test_delivery.py`), Python присваивает ей значение `"__main__"`, и вызывается `unittest.main()`, прогоняя тесты только этого файла. Если же файл импортируется пакетным сборщиком (`python -m unittest discover`), `__name__` равен имени модуля (`"tests.test_delivery"`), условие ложно, и тесты не запускаются преждевременно при импорте.*

**В: В чем прикол и разница между фикстурами `setUp`, `tearDown`, `setUpClass` и `tearDownClass`?**  
*О: Это методы управления жизненным циклом тестов (фикстуры):*
* `setUp(self)` — выполняется **перед каждым** отдельным тестовым методом (подготовка свежих изолированных данных);
* `tearDown(self)` — выполняется **после каждого** теста (очистка ресурсов, даже если тест упал);
* `setUpClass(cls)` (с декоратором `@classmethod`) — выполняется **один раз на весь тестовый класс** перед первым тестом. У нас в `TestLoggingIntegration` используется для единоразовой инициализации логгера (`setup_logging(console=False)`), чтобы не пересоздавать его для каждого теста;
* `tearDownClass(cls)` (с декоратором `@classmethod`) — выполняется **один раз на весь класс** после завершения всех его тестов (закрытие соединений, удаление временных баз данных).
